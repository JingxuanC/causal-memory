## Method

### What is stored

The `Add` endpoint stores every received memory chunk verbatim in SQLite under its `user_id` (the retrieval isolation boundary) with `session_id` grouping and the original timestamp. Storage is synchronous: `Add` returns `200` only after the messages are committed and searchable.

### How retrieval works

`Search` fuses **two signals** per memory and ranks by the combined score:

1. **Lexical (shared-prefix matching)**: tokenize query and memory with the
   project's tokenizer (ASCII word tokens, stop-word filtered; CJK character
   bigrams). A query token matches a memory token when they share a
   **common prefix of ≥ 4 characters** (`editor` ↔ `editing`,
   `deployment` ↔ `deploy`) — one rule that absorbs English morphology
   without a stemmer table. Lexical score = Σ over query tokens of
   `1 + ln(hits)`.
2. **Semantic (offline fastembed)**: when the server is built with
   `--features local-embed`, every stored chunk is embedded at Add time with
   the in-process ONNX model (BAAI/bge-small-en-v1.5, 384 dims, ~130 MB,
   downloaded once, no API key, no runtime network). At Search time the
   query is embedded (with the BGE retrieval instruction prefix) and cosine
   similarity is added to each candidate, weighted `sim × #query-tokens` so
   a semantic hit counts like one lexical hit. No embedder available →
   lexical-only, with no other behavior change.

Results are returned ordered most-relevant first, capped at `top_k`. No
answer generation happens in `Search` — the platform's answer model receives
the returned memory evidence. No state is shared across samples; `user_id`
isolation is enforced in every query.

> macOS note: linking the local ONNX backend on macOS requires a full Xcode
> SDK (the Command-Line Tools CoreML framework lacks classes the bundled
> ONNX Runtime references). The Docker image (Linux) builds and runs the
> fused server out of the box.

### Design notes

- The memory text is the raw chunk (the platform controls which chunks constitute a sample's write stream), so the system is dataset-agnostic.
- The per-user corpus is the scoring scope — evaluation-scale corpora stay tractable without external indexes.
- The full causal-memory system (typed causal edges, spreading activation, consolidation) is not part of this entry's retrieval path; it exists in the same repository as the project's main deliverable.

## Run instructions

### Docker (platform route)

The image builds with `--features local-embed` (semantic fusion included):

```bash
docker build -t causal-memory-amc .
docker run -p 8787:8787 -v amc-data:/data causal-memory-amc
# API entrypoint: http://<host>:8787  (POST /add, POST /search, GET /health)
# DB: /data/amc.db (override with AMC_DB env)
```

### Direct (self-hosted route)

```bash
# Semantic fusion (offline fastembed; needs a full Xcode SDK on macOS):
cargo build --release --bin causal-memory-amc --features local-embed
# Lexical-only (no embedder):
cargo build --release --bin causal-memory-amc
./target/release/causal-memory-amc --db amc.db --port 8787
```

### API contract compliance

- `POST /add` — `{request_id, messages[{role, content, timestamp?}], user_id, session_id}` → `200 {success, request_id, user_id, session_id}` after durable storage.
- `POST /search` — `{query, user_id, top_k, options?}` → `{data: [{id, content, score, created_at?}]}` ordered by relevance; empty `data` when nothing matches.
- `GET /health` — `{status: "ok"}`.
- No authentication on the endpoints themselves; the platform's key flow applies at the deployment layer.
- Internal model usage: none (lexical matching + local ONNX embeddings; no
  LLM API calls) — trivially satisfies the gpt-4o-mini model constraint.

### Self-test

```bash
cargo test -p causal-memory-cli --bin causal-memory-amc   # Add→Search round-trip, isolation, top_k, ordering, morphology
```
